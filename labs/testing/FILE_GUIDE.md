# Карта файлов и сценариев ЛР №2

Для запуска и демонстрации преподавателю начните с
[основной инструкции по защите](DEFENSE.md). Ниже — подробный разбор кода.

Этот гайд объясняет существующий код: кто кого запускает, где находятся проверки, откуда берутся данные и как читать результаты. Команды выполняются из `/home/rudy/projects/cool-magic-battles`.

## 1. С чего начать чтение

Рекомендуемый порядок:

1. `Makefile` — команды входа.
2. `scripts/testing/run.py`: `STAGES`, `execute()`, `pytest()`, `runner()`, `finalize()` — управление всем прогоном.
3. `tests_lab2/integration/test_user_repository_integration.py` — самый простой интеграционный сценарий.
4. `tests_lab2/conftest.py` — откуда берутся аргументы тестов.
5. `scripts/testing/storage.py` — исходные данные и восстановление.
6. Остальные integration-тесты.
7. `tests_lab2/e2e/test_game_lifecycle_e2e.py` и `scripts/testing/scenario.py` — весь HTTP-сценарий.
8. `docker-compose.testing.yml` и `Dockerfile.tests` — где всё исполняется.
9. `scripts/testing/report.py`, `pages.py` и `.github/workflows/testing.yml` — отчётность, CI и GitHub Pages.
10. [Актуальная инструкция для защиты](DEFENSE.md) — свежий прогон, Wireshark и публикация.

## 2. Общая цепочка вызовов

```text
Ты вводишь make test-lab2-demo
  → Makefile запускает Python-скрипт на хосте
  → run.py создаёт уникальные имена и каталоги
  → Docker собирает тестовый образ
  → Compose поднимает PostgreSQL и MinIO
  → wait.py проверяет их доступность
  → storage.py восстанавливает исходные данные и сохраняет baseline
  → pytest запускает первый этап
  → pytest запускает integration
  → поднимается API, pytest запускает HTTP E2E
  → при --replay: curl повторяет сценарий, tcpdump пишет PCAP
  → finalize() восстанавливает данные и проверяет baseline
  → report.py строит Allure
  → Compose удаляет контейнеры и volumes этого прогона
  → run.py сохраняет summary.json и сводный index.html
```

Python-файл с функцией `test_*` не вызывается игровым приложением. Его обнаруживает pytest. В integration тест вызывает приложение; в E2E тест отправляет приложению запросы по сети.

## 3. Команды входа

| Команда | Что делает |
|---|---|
| `make test` | Запускает старый набор из `src/tests` в окружении хоста; не создаёт новый Docker-стенд и не выбирает `tests_lab2` |
| `make test-lab2` | Создаёт стенд, выполняет unit → integration → E2E, восстанавливает данные, сохраняет отчёты |
| `make test-lab2-demo` | То же плюс повторение через curl и запись PCAP |
| `make test-lab2-demo LAB2_ARGS="--repeat-integration"` | Полное демо с двумя integration-прогонами на одном экземпляре PostgreSQL |

Причина различия: в `pytest.ini` стоит `testpaths = src/tests`. Оркестратор второй лабораторной передаёт каталоги pytest явно, поэтому может запускать и `tests_lab2` вне этого значения.

## 4. Файлы окружения

### `Dockerfile.tests`

Описывает образ, внутри которого есть Python, зависимости проекта, pytest и его плагины, Java для Allure 2, Allure CLI, curl и tcpdump. Копирует исходники, миграции и новые тесты в `/app`.

**Образ** — подготовленный шаблон файлов и программ. **Контейнер** — конкретный запущенный процесс на его основе. Из одного образа запускаются контейнер API, одноразовые тестовые контейнеры и захват трафика. Разные команды определяют их роль.

`CMD` в Dockerfile задаёт команду по умолчанию. Оркестратор передаёт свои команды и заменяет её при запуске integration, E2E, reset или генерации отчёта.

### `docker-compose.testing.yml`

Описывает связи сервисов:

| Сервис | Роль |
|---|---|
| `db` | PostgreSQL с отдельной БД `cmb_test` |
| `minio` | Отдельный MinIO, bucket `cards-test` |
| `api` | Uvicorn с `api.app:app`, принимает HTTP на внутреннем порту 8000 |
| `tests` | Шаблон одноразового runner: pytest, reset, wait, Allure, curl replay |
| `capture` | tcpdump в том же сетевом пространстве, что у API |

Внутри Docker API доступно как `http://api:8000`, БД — как `db:5432`. Это имена сервисов во внутренней сети, а не пути на диске.

Монтирование `/artifacts` означает: файл, записанный туда в контейнере, появляется в `build/testing/<run-id>/` на хосте. `/history` связан с постоянным каталогом истории отчётов.

У API снаружи назначается свободный loopback-порт; он записывается в `api-url.txt`. Захват находится внутри его сети, поэтому в Wireshark нужен порт **8000**, а не внешний случайный порт.

`--immediate-mode` и ожидание перед остановкой захвата нужны, чтобы в PCAP попали последние ответы. TShark сопоставляет каждый метод, URI и код ответа с `replay.jsonl`; номера кадров сохраняются в `capture-verification.json`.

### `requirements-testing.txt`, `.dockerignore`, `.gitignore`

- `requirements-testing.txt` подключает основные зависимости и добавляет `pytest-timeout`.
- `.dockerignore` исключает из контекста сборки рабочий `.env`, `.venv`, Git-данные, отчёты и ряд локальных файлов.
- `.gitignore` исключает генерируемый `build/` и позволяет добавить в Git служебные файлы лабораторной.

## 5. Главный управляющий файл: `scripts/testing/run.py`

Это оркестратор: он выполняется **на хосте**, а проверяемое приложение и тестовые команды запускает в контейнерах.

| Часть | Назначение |
|---|---|
| `STAGES` | Указывает каталоги unit, integration, E2E и их порядок |
| `Pipeline.__init__()` | Создаёт run-id, Compose project, каталоги результатов и переменные окружения |
| `command()` | Запускает Compose-команду, ограничивает время, сохраняет её вывод в лог |
| `runner()` | Запускает одноразовый контейнер `tests` с нужной командой |
| `remove_runner()` | Удаляет конкретный одноразовый контейнер при прерывании/таймауте |
| `storage()` | Вызывает `storage.py` внутри runner |
| `pytest()` | Формирует команду pytest, пути отчётов, seed и плагины |
| `start_api()` | Поднимает сервер, ждёт его доступности, сохраняет внешний URL |
| `execute()` | Готовит стенд и проводит этапы; организует повтор и PCAP |
| `finalize()` | Собирает логи, останавливает процессы, восстанавливает baseline, строит Allure и удаляет ресурсы |
| `write_report()` | Читает JUnit XML, пишет итоговый JSON, HTML и сводный тренд |
| `main()` | Разбирает параметры, устанавливает обработчики сигналов, вызывает execute/finalize и возвращает код успеха/ошибки |

`finally` в `main()` означает, что `finalize()` вызывается и после ошибки в основном ходе выполнения. Это не гарантия исполнения при SIGKILL всего процесса или выключении хоста.

### Параметры запуска

| Параметр | Зачем |
|---|---|
| `--run-id name` | Понятное уникальное имя прогона; существующий каталог не перезаписывается |
| `--history-key name` | Отдельная история отчётов, например для разных разработчиков |
| `--fail-stage integration` | Намеренно пометить успешно выполненные тесты этапа как failed, чтобы показать восстановление |
| `--repeat-integration` | После успешного integration восстановить baseline и повторить его на том же экземпляре БД |
| `--replay` | После зелёных этапов повторить HTTP-сценарий через curl и записать трафик |
| `--keep` | Не удалять созданные ресурсы после восстановления; PostgreSQL и MinIO остаются доступны, API остановлен |

После ошибки следующего этапа выполняется только учёт skipped: тела его тестов и фикстуры не запускаются.

## 6. Откуда берутся аргументы тестов: `tests_lab2/conftest.py`

`conftest.py` pytest подхватывает автоматически. Его не нужно импортировать в каждый тест.

```python
def test_user_lifecycle_persists_between_connections(engine, db_session):
    ...
```

Имена аргументов — запросы к pytest на подготовку фикстур:

```text
engine:
  reset() → открыть тестовый SQLAlchemy Engine → yield

db_session(engine):
  открыть Session на этом Engine → yield

тест:
  получить готовые engine и db_session → выполнить шаги

после теста:
  закрыть Session → освободить Engine
```

`service(db_session)` собирает настоящий `GameAppService` с настоящими SQLAlchemy-репозиториями, `CardLogic`, `DeckService` и `GameStateManager`. Передаёт настоящую `db_session`, чтобы покупка дошла до SQL-функции.

`api_url` читает адрес сервера из окружения. E2E запрашивает только эту фикстуру: PostgreSQL baseline ему готовит оркестратор перед этапом, а не его собственная `engine`-фикстура.

Важно: `engine`-фикстура восстанавливает baseline **до** каждого integration-теста. Её teardown закрывает ресурсы, но не отменяет все записи. Итоговое восстановление состояния делает внешний оркестратор.

## 7. Исходные данные: `scripts/testing/storage.py`

| Функция | Что делает |
|---|---|
| `stable_id(name)` | Вычисляет одинаковый UUID для одинакового имени через UUID5 |
| `test_engine()` | Проверяет тестовый режим и имя БД, создаёт SQLAlchemy Engine |
| `object_storage()` | Создаёт клиента только для разрешённого тестового bucket |
| `reset()` | Пересоздаёт public-схему тестовой БД, применяет миграции, заполняет seed, очищает тестовый bucket |
| `snapshot()` | Получает нормализованные значения таблиц, определения функций/триггеров и имена объектов bucket |
| `verify()` | Сравнивает текущий снимок с сохранённым baseline и печатает SHA-256 |

Исходные данные: один heal-тип карты, одна запись изображения с `file=None`, 50 карт с фиксированными ID, `power=1`, `echo=1`, `cost=1`, `cool_points=0`. Пользователей, партий и игроков нет.

Почему именно так: сервис старта выбирает 50 карт из БД; heal-карту можно сыграть без указания противника, получить одно эхо и купить карту за одно эхо. Случайная раздача меняет ID в руке, но не делает сценарий недопустимым.

Исходные данные одинаковы, но созданные во время теста пользователи/партии могут иметь случайные UUID. После reset они исчезают.

Почему не простой rollback: `save()` в репозиториях вызывает commit; API ещё и работает в другом процессе со своими соединениями. Финальный rollback одной тестовой Session не отменит эти изменения.

Миграции находятся в `alembic/versions/`; ревизия `011_card_trigger_and_buy_procedure.py` создаёт проверяемые PostgreSQL-функцию и триггер. Простой `metadata.create_all()` их не заменяет.

## 8. Все пять интеграционных сценариев

Это пять функций pytest в пяти файлах, внутри каждой несколько шагов. `allure.step()` оформляет их в отчёте; отдельными pytest-тестами шаги не становятся.

### 8.1. Пользователь

Файл: `tests_lab2/integration/test_user_repository_integration.py`.

Функция: `test_user_lifecycle_persists_between_connections`.

1. Создаёт User и сохраняет настоящим репозиторием.
2. В новой Session проверяет имя и роль authenticated.
3. Меняет роль на player и проверяет сохранение через новое соединение.
4. Пытается сохранить другого пользователя с тем же именем: ожидает PersistenceError и проверяет, что пользователь остался один.
5. Удаляет пользователя; проверяет `exists=False` и EntityNotFoundError при чтении.

**Проверяемая граница:** User → репозиторий → маппинг/SQLAlchemy → ограничения PostgreSQL.

### 8.2. Карта

Файл: `tests_lab2/integration/test_card_repository_integration.py`.

Функция: `test_card_repository_roundtrip_update_reject_and_delete`.

1. Берёт допустимую seed-карту, присваивает новые ID и название, сохраняет.
2. Через новую Session проверяет карту, связь с изображением и типом heal.
3. Меняет стоимость на 7 — запись допустима.
4. Пытается поставить 8 — ожидается PersistenceError, в БД остаётся 7.
5. Удаляет карту, проверяет исключение при повторном чтении.

**Проверяемая граница:** репозиторий карты, связанные сущности и проверка стоимости PostgreSQL-триггером.

### 8.3. Жизненный цикл игры через сервис

Файл: `tests_lab2/integration/test_game_lifecycle_integration.py`.

Функция: `test_service_game_lifecycle_with_postgres`.

1. Создаёт двух пользователей и партию через `GameAppService`.
2. Вводит обоих в игру; проверяет сохранение участников и повышение роли до player.
3. Повторное вступление того же пользователя должно завершиться ошибкой без появления третьего игрока.
4. Стартует партию; проверяет in_progress, текущего игрока, рынок из пяти карт и руки по пять карт.
5. Завершает ход и проверяет смену игрока.
6. Завершает игру и через новую Session проверяет finished, winner_id и отсутствие текущего игрока.

**Проверяемая граница:** бизнес-сервис + доменная логика + несколько настоящих репозиториев + PostgreSQL.

### 8.4. Покупка карты

Файл: `tests_lab2/integration/test_purchase_integration.py`.

Функция: `test_purchase_function_and_business_service`.

1. Готовит запущенную партию с одним участником, у которого ноль эхо.
2. Пытается купить через сервис: ожидается ValueError.
3. Напрямую вызывает `SELECT purchase_card(...)`: PostgreSQL тоже должен отказать из-за недостаточного эхо.
4. Проверяет, что баланс и рынок не изменились.
5. Через сервис играет карту, получает эхо и покупает карту.
6. Через новую Session проверяет баланс 0, отсутствие карты на рынке и её появление в discard.

Прямой SQL-вызов в негативной части нужен потому, что Python-сервис может отказать раньше, чем выполнится SQL-функция. Эти две проверки доказывают разные части поведения.

### 8.5. Граничные значения триггера

Файл: `tests_lab2/integration/test_card_constraints_integration.py`.

Функция: `test_postgres_card_trigger_boundaries`.

Напрямую обновляет запись SQL-запросами. Принимаются cost=1 и cost=7. Отвергаются cost=0, cost=8, power=0, cool_points=-2 и cool_points=6. После каждой ошибки проверяется, что строка осталась прежней.

**Зачем прямой SQL:** чтобы доказать работу ограничения в самой БД, минуя предварительные проверки Python.

Это конкретный набор границ, а не проверка всех возможных полей и комбинаций триггера.

## 9. E2E и ручной replay

Файл `tests_lab2/e2e/test_game_lifecycle_e2e.py` содержит одну функцию:

```python
def test_game_lifecycle_over_real_http(api_url):
    play_scenario(api_url, steps=True)
```

Основная последовательность находится в `scripts/testing/scenario.py`, функции `play_scenario()`.

| № HTTP-запроса | Действие | Основная проверка |
|---|---|---|
| 1 | Регистрация labhost | Получен ID и роль authenticated |
| 2 | Регистрация labguest | Другой ID, правильная роль |
| 3 | Вход labhost | Вернулся ID зарегистрированного пользователя |
| 4 | Создание labroom | created, правильное имя, игроков ещё нет |
| 5 | Вступление хоста | Один участник |
| 6 | Вступление гостя | Два нужных участника |
| 7 | Старт | in_progress, рынок из 5 карт, у каждого 5 карт в руке и 10 всего |
| 8 | Разыгрывание карты текущим игроком | Карта ушла из hand в table; прибавилось эхо |
| 9 | Покупка | Списалась стоимость; карта ушла с рынка в discard |
| 10 | Конец хода | Другой текущий игрок, номер хода 1, рынок пополнен |
| 11 | Повторное чтение | Сервер вернул сохранённое состояние |
| 12 | Завершение | finished, текущего игрока нет, победитель среди участников |
| 13 | Повторное чтение | Завершённое состояние сохранилось |

При обычном вызове запросы отправляет HTTPX. При `--curl` используется класс `CurlClient`, который запускает реальные процессы curl. Проверки сценария общие, HTTP-клиенты разные; это повтор одного сценария другим инструментом, а не независимый второй набор бизнес-ожиданий.

Вложенная функция `request()` добавляет заголовок пользователя, отправляет JSON, проверяет статус, возвращает JSON-ответ, сохраняет запись/Allure attachment при включённых параметрах.

Различай ID: `X-User-Id` — пользователь, `player_id` — участник конкретной партии, `game_id` — партия. Текущего игрока тест узнаёт из ответа; порядок участников случайный.

Тест не подменяет серверные зависимости и не использует TestClient. При этом UI, Redis-кэш и загрузка картинок в этот сценарий не входят.

## 10. Вспомогательные файлы

### `scripts/testing/wait.py`

Предотвращает запуск тестов до готовности сервисов. Для storage проверяет SQL-запрос и доступность MinIO; для API — `/openapi.json`. Есть конечное ожидание, затем ошибка. Проверка OpenAPI доказывает доступность API-процесса; работоспособность игровых операций подтверждают последующие тесты.

### `scripts/testing/pytest_control.py`

Это pytest-плагин, подключаемый аргументом `-p scripts.testing.pytest_control`.

- `pytest_collection_modifyitems()` при наличии `CMB_SKIP_REASON` добавляет skip-маркеры найденным тестам. Поэтому пропущенный этап виден в JUnit/Allure, а его фикстуры не выполняются.
- `pytest_runtest_makereport()` в режиме `CMB_FAIL_STAGE` меняет успешный результат вызова теста на failed после реальных действий. Это управляемый сбой для демонстрации, а не ошибка правил игры.

Статус «CI job skipped» сам по себе не создаёт сведения о тестах в Allure, поэтому нужен этот отдельный учёт.

### `scripts/testing/report.py`

Собирает Allure 2 HTML. Добавляет служебный результат подготовки/восстановления окружения, переносит предыдущий history в текущие results, запускает Allure CLI, сохраняет новую history.

110 уникальных прикладных тестов плюс одна служебная проверка дают 111 результатов Allure. Повтор integration отображается как повторное выполнение тех же тестов.

Сводный `index.html` строится отдельно в `run.py`; он позволяет увидеть итог и ошибки даже при проблеме генерации Allure.

### `scripts/testing/__init__.py`

Обозначает пакет служебного кода. Сценарий тестирования сам не запускает.

### `.github/workflows/testing.yml`

Автоматический запуск на push, PR и вручную. Получает исходники, восстанавливает историю, вызывает тот же оркестратор в Docker и сохраняет artifacts даже после ошибки. Для одной git ref запуски сериализуются, чтобы не переписывать историю одновременно.

Конфигурация подготовлена. Локальные результаты не являются доказательством успешного удалённого CI: реальный запуск нужно проверить во вкладке Actions после отправки нужных исходников.

## 12. Что находится в каталоге результатов

Каждый запуск пишет `build/testing/<run-id>/`.

| Артефакт | Что искать |
|---|---|
| `summary.json` | Статусы этапов, returncode, cleanup, ошибки, время, commit и dirty_worktree |
| `index.html` | Удобная сводка и тренд; открывается обычным браузером |
| `unit.xml`, `integration.xml`, `e2e.xml` | Машиночитаемые результаты каждого теста, ошибки и skipped |
| `integration-first.xml` | Первый integration при `--repeat-integration` |
| `allure-results/` | Сырые результаты, шаги и вложения; это ещё не HTML |
| `allure-report/` | Сформированный Allure HTML; открывать через HTTP-сервер |
| `coverage/`, `coverage.xml`, `coverage-data` | Покрытие, измеренное на первом этапе |
| `baseline.json` | Ожидаемые исходные данные и определения функций/триггеров |
| `initial-verify.log` | Исходный baseline прошёл проверку |
| `cleanup-verify.log` | После тестов исходное состояние восстановлено |
| `baseline-mismatch.json` | При несовпадении — фактическое состояние для разбора |
| `unit.log`, `integration.log`, `e2e.log` | Подробный вывод pytest соответствующего этапа |
| `build.log`, `wait-*.log` | Проблемы сборки и доступности сервисов |
| `services.log` | Логи серверов; ожидаемые негативные SQL-проверки тоже могут оставлять ERROR в PostgreSQL |
| `demo.pcap` | Сетевые пакеты curl replay |
| `replay.jsonl` | По одной JSON-записи с HTTP-ответом на каждый запрос replay |
| `down.log` | Удаление ресурсов конкретного прогона |

`passed` у всех тестов и `cleanup=failed` — общий неуспешный запуск. Нужно читать оба результата. Слово ERROR в логе БД не обязательно означает падение теста: тест может намеренно отправить недопустимую стоимость и ожидать отказ.

Одновременно в другом:

## 15. Эксплуатация стенда

Перед запуском нужны Docker Engine, Docker Compose и Python 3 на хосте. Тестовые
зависимости и Allure устанавливаются в Dockerfile.tests. Хостовая `.venv` для
runner не нужна. Для запуска существующих pytest-тестов на хосте установите
`requirements-testing.txt` в активированное Python-окружение.

### Восстановление и его пределы

Reset допускается только при `CMB_TESTING=1` и имени PostgreSQL БД `cmb_test`; для объектов разрешён только bucket `cards-test`. Настройки задаются в отдельном Compose-файле. Reset пересоздаёт схему, применяет Alembic, заполняет фиксированные данные и очищает тестовый bucket. В конце сравниваются все значения таблиц, определения функций/триггеров и список объектов с исходным снимком.

Оркестратор находится на хосте и восстанавливает данные после неуспешного pytest, ошибки API, таймаута или SIGINT/SIGTERM оркестратора. При таймауте прерывается и его одноразовый тестовый контейнер. Сначала сохраняются логи, затем останавливаются процессы, восстанавливается baseline, строится отчёт, удаляются выделенные ресурсы. Ошибка cleanup делает общий запуск красным.

В Allure также есть отдельный служебный результат подготовки/восстановления окружения:
поэтому 110 уникальным прикладным тестам соответствует 111 результатов Allure.
Статус тестов и статус восстановления показываются отдельно.

При `SIGKILL` всего оркестратора, падении Docker daemon или выключении машины код finalizer не выполнится. Следующий запуск всегда создаёт новый стенд и исходные данные; оставшийся старый project нужно удалить отдельно по его имени после восстановления Docker. Нельзя обещать очистку кода на выключенном хосте.


### Исторические результаты и текущая проверка

Прогоны 16 октября 2026 года и их доказательства остаются в `build/testing/`:
`lab2-final`, `lab2-wireshark`, `lab2-fail-integration`, `lab2-fail-e2e`,
`lab2-parallel-alice`, `lab2-parallel-bob`. В штатных прогонах было 110 уникальных
прикладных тестов; отдельный Allure-результат фиксирует подготовку/восстановление.
Для демонстрации полного HTTP-сценария используйте `lab2-wireshark/demo.pcap`:
в нём проверялись 13 запросов и 13 успешных ответов. Старые PCAP могли быть неполными.

Исторический зелёный прогон не доказывает успешность текущих исходников.
Новый запуск создавайте с новым `--run-id`; проверяйте exit code, `summary.json`,
`cleanup=verified`, JUnit и PCAP. Локальные ссылки на артефакты после клонирования
нужно восстановить новым запуском или скачать результаты из CI.
Удалённый GitHub Actions считается проверенным только после фактического запуска
workflow на опубликованном составе исходников, включая миграцию 011.

Эти тесты не подтверждают полноту покрытия всего приложения, браузерный UI,
реальный Redis-кэш и все сценарии загрузки изображений.
