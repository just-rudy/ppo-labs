# Лабораторная работа №2: запуск, устройство и защита

Это основная инструкция для запуска и демонстрации лабораторной в Cool Magic
Battles. Подробный разбор отдельных функций находится в [FILE_GUIDE.md](FILE_GUIDE.md).
Исходное задание — [ТИОПО, ЛР №2.pdf](ТИОПО,%20ЛР%20№2.pdf).

## 1. Что именно демонстрируем

Система — игровой HTTP API с бизнес-логикой и PostgreSQL. Для лабораторной
автоматически создаётся отдельный Docker-стенд с PostgreSQL и MinIO.
MinIO — хранилище объектов; его тестовый bucket тоже входит в восстановление.
Frontend для этой лабораторной запускать не нужно: E2E проверяет HTTP API.

На защите нужно показать:

1. Последовательность unit → integration → e2e в отдельном тестовом контейнере.
2. Реальные операции бизнес-логики и репозиториев с PostgreSQL.
3. Полный пользовательский сценарий через HTTP.
4. Остановку последующих этапов после ошибки и восстановление данных.
5. Повторяемость integration и независимость двух локальных запусков.
6. Автоматический отчёт, историю запусков и CI в GitHub Actions.
7. Повторение E2E средствами curl и его сетевой захват в Wireshark.

**Важно:** зелёный локальный отчёт не доказывает запуск в GitHub Actions.
CI нужно показать отдельным фактическим запуском в GitHub. Точно так же старый
PCAP не подтверждает, что текущая версия только что прошла проверку.

## 2. Подготовка компьютера

Команды ниже рассчитаны на Linux. Понадобятся Git, Python 3.10+, Make,
Docker с доступом к daemon, Compose v2 либо docker-compose v1.
Для просмотра PCAP установите Wireshark на хосте.

```bash
cd /home/rudy/projects/cool-magic-battles
python3 --version
make --version
docker version
```

У `docker version` должны отобразиться Client и Server без ошибки доступа.
Затем проверьте установленный вариант Compose:

```bash
docker compose version
```

Если команда отсутствует, проверьте `docker-compose version`: runner умеет
выбирать между двумя вариантами. При ошибке доступа к Docker сначала исправьте
доступ в своей системе и повторите `docker version`. Сам runner права не меняет.

Python-зависимости приложения, pytest, curl, tcpdump, TShark и Allure
устанавливаются **внутри тестового образа**. Для запуска `make test-lab2-demo`
устанавливать их в `.venv` не нужно. Первая сборка требует сети для получения
образов и зависимостей; отключение сети в unit относится к выполнению тестов,
а не к сборке Docker-образа.

Не запускайте `make db-reset` или обычный `docker-compose.yml` для подготовки
лабораторной. У неё свой файл `docker-compose.testing.yml`, свои данные
и автоматическая инициализация. Файл `.env` с рабочими настройками не нужно
менять для лабораторного стенда.

## 3. Быстрый запуск перед защитой

```bash
cd /home/rudy/projects/cool-magic-battles
make test-lab2-demo LAB2_ARGS="--repeat-integration"
```

Эта команда создаёт уникальный ID запуска автоматически. Сохраните его из вывода:
все результаты находятся в `build/testing/<run-id>/`.

В нормальном прогоне выполняется следующее:

1. Сборка тестового образа и запуск PostgreSQL и MinIO.
2. Миграции, начальные данные, сохранение и проверка baseline.
3. Unit-тесты с отключёнными сетевыми сокетами и расчётом покрытия.
4. Integration-тесты, сброс данных и повтор integration на той же БД.
5. Запуск API и HTTP E2E.
6. Сброс данных, повтор сценария через curl с захватом tcpdump.
7. Проверка захвата с помощью TShark.
8. Остановка процессов, восстановление и проверка baseline.
9. Генерация Allure, удаление стенда и создание итоговой сводки.

В конце ожидаются код завершения 0 и поля в `summary.json`:

```json
{
  "stages": {
    "unit": {"status": "passed", "returncode": 0},
    "integration": {"status": "passed", "returncode": 0},
    "e2e": {"status": "passed", "returncode": 0}
  },
  "cleanup": "verified",
  "errors": [],
  "integration_repeated_on_same_instance": true,
  "capture": "verified"
}
```

Это фрагмент ожидаемой структуры, а не полный файл и не результат нового запуска.
Не ориентируйтесь на фиксированное количество тестов: оно меняется при добавлении
проверок. Основные признаки успеха — статусы этапов, пустой `errors` и проверка
восстановления. Сводный счётчик не добавляет первый повтор integration повторно;
для него отдельно сохраняются `integration-first.xml` и `integration-first.log`.

Для просмотра отчёта запустите во втором терминале:

```bash
cd /home/rudy/projects/cool-magic-battles
python3 -m http.server 8765 --directory build/testing
```

Откройте `http://localhost:8765/`, выберите каталог своего запуска и `index.html`.
Из сводки перейдите в Allure и coverage. Allure открывайте через HTTP-сервер,
а не двойным щелчком по HTML-файлу.

## 4. Какие команды для чего нужны

| Команда | Назначение |
|---|---|
| `make test-lab2` | Unit → integration → E2E, восстановление, отчёты |
| `make test-lab2-demo` | То же плюс curl и PCAP |
| `make test-lab2-demo LAB2_ARGS="--repeat-integration"` | Рекомендуемый полный прогон для защиты |
| `make test-lab2 LAB2_ARGS="--fail-stage integration"` | Намеренная ошибка integration и демонстрация восстановления |
| `make test-lab2 LAB2_ARGS="--fail-stage e2e"` | Намеренная ошибка E2E и восстановление |
| `make test-lab2 LAB2_ARGS="--history-key defense"` | Запуск с отдельной историей отчётов |
| `make test` | Старый набор `src/tests` на хосте; Docker-стенд ЛР №2 не создаёт |

Аргументы можно объединять в одном `LAB2_ARGS`. По умолчанию история локальных
запусков общая: ключ `local`. Для собственной последовательности трендов
используйте один и тот же `--history-key` в нескольких запусках.

`--run-id` задаёт имя каталога и Compose project. Разрешены строчные латинские
буквы, цифры, `_` и `-`, первый символ — буква или цифра, длина до 80 символов.
ID нельзя использовать повторно: каталог результатов должен быть новым.
Проще не указывать этот параметр и оставить автоматическую генерацию.

`--keep` сохраняет ресурсы для диагностики после очистки данных. Это не режим
сохранения работающего API: в финализации процессы останавливаются. Для обычной
защиты этот флаг не нужен.

Связь компонентов при полном прогоне:

```text
make test-lab2-demo
  └─ run.py на хосте
      └─ docker-compose.testing.yml, project cmbtest-<run-id>
          ├─ db: отдельный PostgreSQL и volume
          ├─ minio: отдельный bucket и volume
          ├─ tests: одноразовые контейнеры из Dockerfile.tests
          │   ├─ storage.py → Alembic → схема и начальные данные
          │   ├─ pytest unit → изолированные проверки
          │   ├─ pytest integration → сервисы/репозитории → db
          │   ├─ pytest e2e → scenario.py/HTTPX → api → db
          │   ├─ scenario.py/curl → api → db
          │   ├─ capture.py/TShark → проверка demo.pcap
          │   └─ report.py → Allure и история
          ├─ api: Uvicorn/FastAPI
          └─ capture: tcpdump в сетевом пространстве api

/artifacts в контейнере ↔ build/testing/<run-id>/ на хосте
/history в контейнере   ↔ build/testing/history/<history-key>/ на хосте
```

Сервисы внутри сети обращаются друг к другу по именам: `api:8000`, `db:5432`,
`minio:9000`. Внешний порт API выбирается автоматически и записывается
в `api-url.txt`. После обычного завершения стенд удалён, поэтому этот URL уже
не отвечает. Сохранённые отчёты и PCAP продолжают быть доступны.

### Какие именно тесты запускаются

Определение этапов находится в `STAGES` файла `run.py`:

| Этап | Каталоги | Что подтверждает |
|---|---|---|
| unit | `src/tests/domain`, `src/tests/application`, `src/tests/infrastructure`, `tests_lab2/runner` | Поведение компонентов без сетевых обращений, проверки runner |
| integration | `tests_lab2/integration` | Работу с настоящим PostgreSQL и сохранение изменений |
| e2e | `tests_lab2/e2e` | Пользовательский сценарий через настоящий HTTP API |

Не все старые тесты `src/tests` входят в этот pipeline. В частности, старые
SQLite-тесты из `src/tests/integration` и TestClient-тесты `src/tests/api`
не являются этапом PostgreSQL integration или реальным HTTP E2E лабораторной.

## 6. Как объяснить интеграционные тесты

Начните с `test_user_repository_integration.py`: он проще остальных.
Fixture подготавливает baseline, тест сохраняет пользователя через настоящий
репозиторий, а затем проверяет результат через новую SQLAlchemy Session.
Новая Session нужна, чтобы проверить сохранённое состояние, а не только объект
в памяти предыдущей сессии.

| Файл в `tests_lab2/integration/` | Сценарий |
|---|---|
| `test_user_repository_integration.py` | Создание, изменение, конфликт username, удаление пользователя |
| `test_card_repository_integration.py` | Сохранение и изменение карты, отказ при недопустимой цене, удаление |
| `test_card_constraints_integration.py` | Границы стоимости и запрет недопустимых значений SQL-триггером |
| `test_game_lifecycle_integration.py` | Создание игры, присоединение, старт, смена хода, завершение через сервис |
| `test_purchase_integration.py` | Отказ при недостатке ресурса и успешная покупка, включая SQL-функцию |

Внутри каждого файла один многошаговый сценарий; шаги оформлены `allure.step`.
Для отрицательных проверок используется `pytest.raises`. Обратите внимание
преподавателя и на проверку отказа, и на неизменность сохранённых данных после него.

## 7. Что происходит с данными

`storage.py` разрешает разрушительные операции только при тестовых настройках:
`CMB_TESTING=1`, PostgreSQL и БД `cmb_test`; для MinIO требуется bucket `cards-test`.
Само разделение экземпляров обеспечивается отдельным Compose project и volumes.

Исходное состояние создаётся так:

1. Пересоздаётся схема `public` тестовой БД.
2. Alembic применяет миграции до `head`.
3. Данные миграций заменяются детерминированным набором: один тип карты,
   одна запись изображения и 50 карт со стабильными UUID.
4. Тестовый bucket создаётся при необходимости и очищается.
5. Снимок записывается в `baseline.json`.

В начале каждого integration-теста fixture `engine` вызывает `reset()`.
Между этапами runner тоже восстанавливает исходные данные. Поэтому тесты
не зависят от результатов предыдущего сценария.

В `finalize()` останавливаются процессы стенда, снова выполняется reset,
а затем `verify` сравнивает состояние с исходным снимком: все таблицы, определения
функций, триггеров и список объектов bucket. При совпадении в лог записывается
`BASELINE VERIFIED sha256=...`, в сводку — `cleanup: verified`.
После проверки обычный прогон удаляет контейнеры, сеть и volumes своего проекта.
Это восстановление детерминированного baseline, а не откат одной SQL-транзакции.

Шина сообщений в стенде не используется, Redis отключён. Пользователь определяется
через `X-User-Id`; отдельного реестра активных login-сессий нет. Поэтому отдельные
операции вычитывания очереди и удаления серверных login-сессий здесь не требуются.

## 8. Где искать результаты

Все пути в таблице относительно `build/testing/<run-id>/`.

| Файл или каталог | Что показать |
|---|---|
| `index.html` | Общая сводка, статусы, тренды и ссылки |
| `summary.json` | Машиночитаемые статусы, ошибки, commit, признак изменённой рабочей копии, cleanup |
| `unit.xml`, `integration.xml`, `e2e.xml` | JUnit-результаты, в том числе skipped |
| `integration-first.xml`, `integration-first.log` | Первый integration-прогон при `--repeat-integration` |
| `allure-results/` | Исходные данные для Allure |
| `allure-report/` | Готовый HTML Allure: Suites, шаги, History, Trends |
| `coverage/index.html`, `coverage.xml` | Покрытие строк и ветвлений unit-тестами |
| `baseline.json` | Сохранённое исходное состояние |
| `cleanup-reset.log`, `cleanup-verify.log` | Восстановление и подтверждение baseline |
| `services.log` | Логи сервисов до их остановки |
| `build.log` | Сборка тестового образа |
| `unit.log`, `integration.log`, `e2e.log` | Вывод соответствующих этапов |
| `demo.pcap` | Реальные пакеты curl-сценария |
| `replay.jsonl` | Метод, путь, статус и JSON ответа для каждого запроса curl |
| `http-packets.tsv` | HTTP-пакеты, декодированные TShark |
| `capture-verification.json` | Сопоставленные номера кадров запросов и ответов |
| `capture-verify.log` | Итог проверки полноты захвата |

Набор файлов зависит от того, до какого места дошёл запуск. Если не собрался
образ, полноценного Allure и PCAP может не быть; сначала смотрите `errors`
в сводке и `build.log`.

В `build/testing/history/<history-key>/` сохраняются `trends.json` и история
Allure `current/`. Свежий запуск с тем же ключом подхватывает историю. Для показа
трендов выполните хотя бы два прогона с одним ключом. Старый HTML-отчёт не
перестраивается после нового запуска — открывайте последний.

## 9. Сценарий защиты: что открыть и что сказать

Перед занятием выполните полный прогон и подготовьте вкладки: код, сводка,
Allure, GitHub Actions, Pages, Wireshark. Полную сборку лучше завершить заранее,
чтобы не тратить защиту на скачивание зависимостей.

| Шаг | Действие | Короткое объяснение преподавателю |
|---|---|---|
| 1 | Открыть `docker-compose.testing.yml` и `Dockerfile.tests` | «Это отдельный стенд с PostgreSQL и MinIO; тесты выполняются в своём контейнере» |
| 2 | Показать `STAGES` и `execute()` в `run.py` | «Runner задаёт unit → integration → e2e, подготовку данных и обработку ошибок» |
| 3 | Запустить полный прогон или показать свежий завершённый | «Здесь integration выполняется дважды на одном экземпляре БД» |
| 4 | Открыть сводку и `summary.json` | «Все этапы прошли, захват проверен, исходные данные восстановлены» |
| 5 | Открыть Allure → Suites → integration | «Это реальные сохранения и чтения PostgreSQL; вот положительные и отрицательные шаги» |
| 6 | Показать код user repository-теста | «Результат проверяется в новой Session, значит изменение действительно сохранено» |
| 7 | Открыть E2E в Allure и `scenario.py` | «Один сценарий проходит от регистрации до завершения игры через HTTP» |
| 8 | Показать PCAP в Wireshark | «Тот же сценарий повторён через curl, запросы и ответы захвачены tcpdump» |
| 9 | Показать намеренно упавший прогон | «После integration E2E пропущен, но отчёт сформирован и baseline восстановлен» |
| 10 | Показать `cleanup-verify.log` и код `verify()` | «Сравнивается состояние таблиц, SQL-функций, триггеров и bucket» |
| 11 | Открыть GitHub Actions и Pages | «В CI запускается тот же runner; отчёт публикуется автоматически» |
| 12 | Открыть Trends и результаты двух параллельных запусков | «Есть история результатов и изоляция окружений разных разработчиков» |

Если времени мало, основной маршрут — шаги 1–10; для CI, трендов и независимости
держите готовые результаты. Факт запуска CI нельзя заменять показом YAML-файла.

## 10. Wireshark: как показать запросы

Захват выполняется автоматически при `make test-lab2-demo`: curl отправляет
запросы, tcpdump пишет трафик API на порту 8000, TShark проверяет результат.
Wireshark на хосте нужен для просмотра уже сохранённого файла; выбирать
сетевой интерфейс и запускать новый захват на компьютере не нужно.

1. Откройте **File → Open → `build/testing/<run-id>/demo.pcap`**.
2. Введите фильтр `http`.
3. Если HTTP не распознан: **Analyze → Decode As → TCP port 8000 → HTTP**.
4. Введите `http.request` и покажите 13 запросов.
5. Введите `http.response` и покажите 13 ответов.
6. Выберите запрос регистрации или покупки, нажмите правой кнопкой
   **Follow → TCP Stream**. Покажите метод, путь, заголовки, JSON и ответ.
7. Для покупки используйте `http.request.uri contains "/buy"`.
8. Сопоставьте номера кадров с `capture-verification.json`.

Порядок HTTP-сценария:

| Номер | Запрос | Что проверяет сценарий |
|---|---|---|
| 1–2 | `POST /api/v1/users/register` | Созданы два разных пользователя |
| 3 | `POST /api/v1/users/login` | Вход возвращает первого пользователя |
| 4 | `POST /api/v1/game/new` | Создана игра `labroom` |
| 5–6 | `POST /api/v1/game/join` | В игре два участника |
| 7 | `POST /api/v1/game/<id>/start` | Игра началась, созданы руки игроков и рынок |
| 8 | `POST /api/v1/game/<id>/play` | Карта перешла из руки на стол, изменился ресурс |
| 9 | `POST /api/v1/game/<id>/buy` | Карта куплена, ресурс списан, рынок изменён |
| 10 | `POST /api/v1/game/<id>/end-turn` | Текущий игрок сменился |
| 11 | `GET /api/v1/game/<id>` | Состояние сохранено и читается повторно |
| 12 | `POST /api/v1/game/<id>/finish` | Игра завершена и определён победитель |
| 13 | `GET /api/v1/game/<id>` | Завершённое состояние сохранилось |

Внешний случайный порт из `api-url.txt` не нужен для фильтра: tcpdump работает
в сети API, где порт всегда 8000. Curl создаёт отдельные соединения, поэтому
один TCP Stream обычно показывает один обмен, а не весь игровой сценарий.

HTTPX E2E и curl вызывают одну функцию `play_scenario()`. Проверяются не только
коды HTTP, но и поля ответов. Проверка PCAP отдельно сопоставляет метод, URI
и статус каждого ответа с `replay.jsonl`; отсутствие пары приводит к ошибке
прогона. В PCAP видны тестовые пароли, поскольку стенд использует обычный HTTP.
Используйте демонстрационные учётные записи, предусмотренные сценарием.

## 11. Как показать ошибку и восстановление

```bash
make test-lab2 LAB2_ARGS="--fail-stage integration --history-key defense"
```

Ненулевой код завершения здесь ожидаем. Плагин `pytest_control.py` меняет
успешный результат выбранного этапа на failed **после выполнения действий теста**.
Это демонстрирует восстановление реально изменённых данных.

Откройте новый каталог запуска и покажите:

- `summary.json`: integration — failed, e2e — skipped, cleanup — verified.
- Allure или `e2e.xml`: тесты следующего этапа отмечены как skipped.
- `cleanup-reset.log`: восстановление выполнено.
- `cleanup-verify.log`: есть `BASELINE VERIFIED`.

Повторите для E2E при необходимости:

```bash
make test-lab2 LAB2_ARGS="--fail-stage e2e --history-key defense"
```

При ошибке E2E последующих тестовых этапов уже нет; curl replay не запускается,
но восстановление и отчёт всё равно выполняются. Для демонстрации ошибки unit
доступен `--fail-stage unit`: оба следующих этапа будут skipped.

Ctrl+C и SIGTERM обрабатываются runner и запускают финализацию. SIGKILL,
недоступный Docker или выключение компьютера не позволяют гарантировать
выполнение cleanup; не обещайте откат при таких условиях. Проверяйте конкретный
результат `cleanup`, а не только сам факт завершения команды.

## 12. Повторяемость и параллельные разработчики

Повторяемость на одном экземпляре проверяет `--repeat-integration`:
сначала integration, затем reset/verify, затем снова integration.
Покажите `integration-first.log`, `integration.log` и поле
`integration_repeated_on_same_instance` в сводке.

Для независимости создайте два терминала. В первом:

```bash
make test-lab2 LAB2_ARGS="--history-key alice"
```

Одновременно во втором:

```bash
make test-lab2 LAB2_ARGS="--history-key bob"
```

ID сформируются автоматически. У двух запусков должны различаться `run_id`
и `project`; каждый должен получить passed на всех этапах и cleanup verified.
Разные проекты имеют собственные сеть, PostgreSQL, MinIO, volumes, образ
и внешний порт API. Разные ключи истории разделяют ещё и историю отчётов.

Последовательные задания GitHub Actions сами по себе не доказывают локальную
параллельность: для этого покажите именно эти два одновременно запущенных стенда.

## 13. GitHub Actions и GitHub Pages

В репозитории откройте **Settings → Pages → Build and deployment → Source →
GitHub Actions**. Это однократная настройка. Изменения workflow и исходников
должны быть отправлены в GitHub: локальные файлы автоматически туда не попадают.

Workflow `.github/workflows/testing.yml` запускается на push, pull request
и вручную через **Actions → Testing lab 2 → Run workflow**. Для обычного запуска
оставьте `fail_stage` пустым. Для демонстрации ошибки выберите этап в этом поле.

В workflow два jobs:

| Job | Что делает |
|---|---|
| `tests` | Checkout, восстановление истории, полный Docker-прогон с повтором integration и PCAP, загрузка артефактов |
| `pages` | Публикация подготовленной сводки, Allure и coverage |

Внутри job `tests` видны отдельные шаги Prepare, Unit, Integration, E2E, Curl
replay и Restore baseline and generate reports. Они вызывают runner с разными
`--phase`, но сохраняют один Compose project через `pipeline-state.json`.
После ошибки следующие тестовые шаги пропускаются; финализация с `if: always()`
записывает skipped в отчёты и восстанавливает baseline.
Падение этапа делает тестовый job красным; сохранение отчётов выполняется
с `if: always()`. При готовой сводке публикация Pages тоже допускается после
падения тестов. Само наличие сайта не означает, что тесты зелёные.

Pages публикуется из лабораторной ветки `regular` и из основной ветки, включая
ручной запуск на них. Pull request и остальные ветки не обновляют сайт. Адрес смотрите у environment
`github-pages` или в job `pages`: он выводится после фактической публикации.
Если Pages ещё не настроен, тесты могут пройти, а job публикации — упасть.

На странице завершённого workflow в разделе **Artifacts** находятся:

- `lab2-ci-<run_id>-<attempt>` — все результаты, включая PCAP и логи.
- `lab2-history-<key>` — история отчётности для следующего запуска этой ветки.

Артефакты настроены на хранение 30 дней. История привязана к Git ref и
восстанавливается из предыдущего доступного артефакта. Ошибка получения истории
не блокирует тестовый прогон. Если история истекла, тренды начинаются заново.

На Pages копируются `index.html`, `summary.json`, `allure-report/`, `coverage/`.
Отдельные служебные логи, `replay.jsonl` и PCAP туда не копируются; скачивайте
их из полного артефакта. Allure содержит свои данные и вложения тестов.
Сайт показывает последний опубликованный запуск разрешённой ветки, а не каталог
всех старых HTML-отчётов; предыдущие результаты доступны в трендах и артефактах.

## 14. Частые проблемы

| Симптом | Что проверить |
|---|---|
| `permission denied` или `Operation not permitted` при Docker | `docker version` должен видеть Server; проблема до выполнения тестов |
| Нет Compose | Проверить `docker compose version` и `docker-compose version` |
| `pull access denied for minio/minio` | Используется старая версия Compose; обновить код с `Dockerfile.minio`, затем запустить новый прогон |
| Не собирается образ | `build.log`, доступность реестров, установки зависимостей и Allure |
| ID уже существует | Не повторять `--run-id`; оставить генерацию автоматически |
| API не готов | `wait-api-*.log`, `api-*.log`, `services.log` |
| Ошибка интеграции | `integration.log`, шаги Allure, затем `cleanup-verify.log` |
| В сводке нет `capture` | Проверить `--replay`; при падении этапа replay не выполняется |
| PCAP пустой или проверка не прошла | `capture-start.log`, `capture-stop.log`, `capture-verify.log`, `services.log` |
| Wireshark не показывает HTTP | Decode As для внутреннего TCP-порта 8000 |
| Allure пуст при открытии файлом | Открывать через `python3 -m http.server` |
| Тренды показывают один запуск | Выполнить второй с тем же history key и открыть новый отчёт |
| Pages не обновился | Ветка `regular` или основная, настройки Pages, результат job `pages`; если environment ограничивает ветки, разрешить `regular` в Settings → Environments → github-pages |
| `cleanup` не `verified` | Восстановление не подтверждено; изучить `errors` и cleanup-логи |

## 15. Короткие ответы на вопросы преподавателя

| Вопрос | Ответ и место в коде |
|---|---|
| Где запускаются тесты? | В контейнерах `tests`, команда задаётся `Pipeline.pytest()` в `run.py` |
| Как организован порядок? | `STAGES` и цикл в `execute()` |
| Чем integration отличается от unit? | Реальное взаимодействие с PostgreSQL и проверка сохранений через новые Session |
| Чем E2E отличается от integration? | Запрос идёт через HTTP API, а не прямой вызов сервиса/репозитория |
| Откуда тестовые данные? | `storage.reset()`, миграции Alembic и детерминированные UUID |
| Что восстанавливается после ошибки? | Исходное состояние тестовой БД и bucket; `finalize()` → reset → verify |
| Откуда skipped? | Следующие этапы собираются pytest с пропускающей меткой из `pytest_control.py`, их fixtures не выполняются |
| Где отчётность? | `report.py` создаёт Allure, `run.py` — сводку и тренды |
| Что даёт Pages? | Доступный по HTTP опубликованный отчёт; само приложение на Pages не запускается |
| Чем сняты пакеты? | tcpdump сервиса `capture`, анализ TShark, просмотр Wireshark |
| Почему curl и E2E одинаковые? | Оба используют `play_scenario()`, различается HTTP-клиент |
| Сколько процессов pytest? | Один процесс pytest на этап; повтор integration и запись skipped запускаются отдельными вызовами, xdist не используется |
| Почему разработчики не мешают друг другу? | Уникальные Compose projects и отдельные ресурсы каждого прогона |

## 16. Что считать готовностью к защите

Перед защитой должны быть доступны:

- Свежий успешный полный прогон с повтором integration и проверенным PCAP.
- Два запуска с общей историей, чтобы показать тренды.
- Прогон с намеренной ошибкой integration и подтверждённым восстановлением.
- Результаты двух одновременно запущенных стендов.
- Завершённый запуск GitHub Actions и опубликованный отчёт Pages.
- Открытый PCAP в Wireshark с запросами, ответами и JSON.

Этот документ описывает команды и критерии проверки. Он не утверждает, что
в текущей сессии уже выполнены Docker-прогоны или публикация: это подтверждают
только соответствующие логи, артефакты и страница фактического CI-запуска.
